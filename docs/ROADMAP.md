# Путь к коммерческой версии

LoadWatch сейчас — законченный проект для портфолио на одном маленьком VPS. Архитектура заложена так, чтобы превратить его в коммерческий сервис без переписывания:

- API не хранит состояния;
- все лимиты — в конфиге;
- слои «роутеры → сервисы → репозитории»;
- любое изменение схемы — миграцией;
- нотификаторы и верификаторы подключаются через реестры;
- runner атомарно забирает запуски из очереди.

Ниже — что для этого нужно. Ничего из этого сейчас не реализовано: это сознательные границы объёма.

## 1. Учётные записи

| Что | Как | Где опора в коде |
| --- | --- | --- |
| **Подтверждение email** | Таблица одноразовых токенов, письмо через `EmailNotifier`/SMTP, флаг `users.email_verified_at`; без подтверждения — только просмотр | `AuthService.register`, шаблоны Jinja2 |
| **Сброс пароля** | Одноразовый токен (хэш в БД, срок 1 ч), письмо со ссылкой, rate limit | `security/passwords.py`, `notifications/messages.py` |
| **Сессии** | Refresh-токены в httpOnly-cookie вместо JWT в `localStorage`, отзыв сессий, CSRF-защита | `security/tokens.py`, `api/deps.py` |
| **2FA** | TOTP для владельцев сайтов | `AuthService.login` |

## 2. Роли и админка

- Организации и команды: `organizations`, `memberships(role)`; сайты принадлежат организации, а не пользователю. Проверка владельца уже собрана в репозиториях (`get_owned`) — меняется одно место.
- Роли: owner / admin / member / viewer, проверка в зависимостях FastAPI.
- Админ-панель: пользователи, сайты, очередь, ручная блокировка злоупотреблений, просмотр алертов по всем сайтам.

## 3. Квоты и тарифы

- Таблица `plans` (лимиты RPS, длительности, числа сайтов и сценариев, частоты расписания, хранения истории) и `subscriptions`.
- Лимиты пользователя = `min(лимит тарифа, лимит сервера)`. Обрезка параметров уже идёт через `ProfileLimits` — в неё добавится тариф.
- Учёт потребления (запросо-минуты, байты) — из уже собираемых `run_metrics`.

## 4. Биллинг

- Платёжный провайдер (ЮKassa или Stripe) через вебхуки, идемпотентная обработка событий.
- Счета, пробный период, понижение тарифа с мягкой деградацией (расписания на паузу, история сохраняется).

## 5. Распределённые runner'ы

Сейчас один процесс runner на сервере API. Дальше:

1. **Отдельные машины для генерации.** Runner уже общается с API только через БД, а захват запуска атомарный (advisory lock + `SKIP LOCKED`). Несколько runner'ов на разных серверах заработают сразу; `MAX_GLOBAL_CONCURRENT_RUNS` станет лимитом на пул.
2. **Очередь сообщений** (Redis Streams, NATS или RabbitMQ) вместо опроса БД — меньше задержка старта и нагрузка на базу.
3. **Гео-распределённые узлы генерации**: тест из нескольких регионов, метрики с тегом региона. Узлы получают задание с подписью и закреплённым IP; секреты расшифровываются только на узле ключом региона.
4. **Изоляция генератора**: узел в контейнере с egress-фильтром на уровне сети (а не только в коде) — вторая линия защиты от SSRF.

## 6. Масштабирование хранения

- Посекундные ряды — в TimescaleDB или ClickHouse; агрегаты остаются в PostgreSQL.
- Кэш дашборда (Redis), материализованные представления для периодов 30–365 дней.
- Rate limiting и антиспам алертов — в Redis, общий для всех воркеров API.

## 7. Наблюдаемость и эксплуатация

- Prometheus-метрики самого сервиса (очередь, длительность запусков, ошибки доставки уведомлений), Grafana, алерты.
- Структурированные JSON-логи, трассировка (OpenTelemetry).
- Повторная доставка уведомлений с очередью и экспоненциальной задержкой — сейчас при сбое канала уведомление о восстановлении не повторяется.
- Резервные копии БД (pg_dump + хранение вне сервера), проверка восстановления.

## 8. Продукт

- Публичные статус-страницы сайта по SLO.
- Сравнение двух запусков бок о бок, «до и после деплоя».
- Импорт сценариев из HAR и OpenAPI.
- Интеграции: GitHub Checks (результат теста в PR), PagerDuty и Opsgenie.
