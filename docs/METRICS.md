# Метрики

## Для каждого запроса

| Метрика | Как считается |
| --- | --- |
| `dns_ms` | Время резолва имени сайта перед запуском. IP закрепляется на весь тест, поэтому DNS-время получают только запросы, открывшие новое соединение; на переиспользованных соединениях — 0 |
| `connect_ms` | Установка TCP-соединения (trace-расширение httpx) |
| `tls_ms` | TLS-рукопожатие (для `https`) |
| `ttfb_ms` | От отправки заголовков запроса до получения заголовков ответа |
| `transfer_ms` | Скачивание тела (не больше `MAX_RESPONSE_BYTES`) |
| `total_ms` | Весь запрос целиком |
| статус, байты, шаг | Код ответа, объём на проводе, имя шага |

Каждый запрос ограничен `REQUEST_TIMEOUT_SEC` целиком. Ошибки классифицируются: `connect_timeout`, `read_timeout`, `connect_error`, `tls_error`, `protocol_error`, `request_deadline`, `http_<код>`, `assert_failed`, `extract_failed`, `missing_secret`, `invalid_header`…

## Агрегаты запуска

- RPS запросов и проходов в секунду;
- задержка: min / avg / max и перцентили p50 / p90 / p95 / p99;
- доля ошибок, распределение кодов ответов, топ типов ошибок (до 20: девятнадцать самых частых и `other`);
- средние тайминги и p95 TTFB;
- байты отправленные и полученные;
- проходы: успешные, неуспешные, сброшенные (все слоты заняты), прерванные (тест закончился или отменён) и длительность прохода;
- **всё то же — по каждому шагу**;
- посекундный ряд (RPS, проходы, p95, ошибки), сжатый до ~300 точек.

**Перцентили** считаются по логарифмическим корзинам шириной 1%. Это потоковая гистограмма: память не зависит от числа запросов, а погрешность перцентиля — не больше ~0,5%. Минимум, максимум, среднее и количество — точные.

## Apdex

```
Apdex(T) = (satisfied + tolerating / 2) / total
satisfied  — успешные запросы с задержкой ≤ T
tolerating — успешные запросы с задержкой ≤ 4T
ошибки     — всегда «frustrated»
```

`T` задаётся в сценарии (`apdex_t_ms`, по умолчанию 500 мс). Apdex считается для всего запуска и для каждого шага. Значение от 0 до 1: 0,94 и выше — отлично, ниже 0,7 — пользователи страдают.

## SLO

В сценарии задаются `slo_p95_ms` и/или `slo_max_error_rate`. Для каждого запуска сохраняется `slo_met`:

- `true` — p95 не выше цели и доля ошибок не выше цели;
- `false` — нарушено хотя бы одно;
- `null` — SLO не задан или в запуске не было запросов.

Сравнение идёт по точным, неокруглённым значениям: одна ошибка на 30 000 запросов нарушает SLO «0 ошибок». На дашборде — индикатор последнего запуска и **процент запусков в SLO** за период (только по запускам, где SLO задан).

## Регрессии

После каждого успешного запуска он сравнивается с **медианой последних 5 сопоставимых запусков**: тот же сценарий, те же параметры (включая Apdex T), завершён успешно, без насыщения генератора и не оборван лимитом полосы. Нужно минимум 3 таких запуска.

| Метрика | Регрессия, если (по умолчанию) |
| --- | --- |
| p95 | выросла больше чем на 30% **и** больше чем на 10 мс |
| Доля ошибок | выросла больше чем на 2 процентных пункта |
| Apdex | упал больше чем на 0,1 |
| Потолок (ступенчатый тест) | упал больше чем на 20% |

Пороги — в конфиге (`REGRESSION_*`). Медиана устойчива к единичному выбросу. Результат сохраняется структурно и показывается на языке пользователя: «p95 выросла на 40% относительно медианы последних 5 запусков (100 → 140 мс)».

## Потолок (`ceiling_rps`)

Есть только у ступенчатого профиля (`step`). Ступень оценивается целиком: ошибок не больше `max_error_rate` и, если задан, p95 не выше `max_p95_ms`. Потолок — **фактический RPS запросов** последней прошедшей ступени.

- Прошли все ступени или тест оборвал лимит полосы → потолок помечается как нижняя граница (`ceiling_is_lower_bound`): настоящий потолок выше.
- Генератор насытился → потолка нет.

## `generator_saturated`

Генератор сам следит, успевает ли он. Каждую секунду проверяются два признака:

- **лаг event loop.** Раз в 100 мс фоновая задача засыпает и меряет, насколько позже проснулась. Если медиана опоздания за секунду выше `GENERATOR_LAG_THRESHOLD_MS` (3 мс), секунда плохая. Замер: у здорового генератора медиана ≤ 0,5 мс даже на 1000 RPS, у насыщенного — 5–6 мс. Секунда без единого замера (loop стоял всю секунду) — тоже плохая;
- **загрузка процессора.** Если процесс генератора занял за секунду не меньше `GENERATOR_CPU_THRESHOLD` (0,9) ядра — секунда плохая.

`GENERATOR_SATURATION_SECONDS` (3) плохих секунд подряд означают, что не справляется уже генератор, а не сайт.

Такой запуск получает флаг `generator_saturated = true`:

- в интерфейсе и PDF он помечен предупреждением «цифры недостоверны»;
- он не участвует в базовой линии регрессий и не получает оценку регрессии;
- ступенчатый тест останавливается без потолка.

В отчёте есть статистика лага: p50, p95, максимум.

## Хранение

Агрегаты запусков хранятся всегда. Посекундные ряды удаляются через `RETENTION_DAYS` (90 дней) командой `python -m loadwatch.maintenance`.
